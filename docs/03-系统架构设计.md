# 03 系统架构设计

## 1. 架构总览

系统采用**分层架构**：核心为"解析 → 领域 → 存储"三层，外围为 API 层、后台计算层与检查层。依赖方向严格自上而下，领域层通过接口反向依赖存储层（依赖倒置），保证存储可替换、领域逻辑可独立测试。

```
                     ┌─────────────────────────────────────────┐
                     │              web/（前端，静态资源）        │
                     └──────────────────┬──────────────────────┘
                                        │ HTTP
                     ┌──────────────────▼──────────────────────┐
                     │            internal/api（API 层）         │
                     │  router / handlers（含 DTO 绑定与中间件）    │
                     └───────┬──────────────────────┬───────────┘
                             │ 调用领域服务            │ 提交/查询任务
              ┌──────────────▼───────────┐   ┌───────▼──────────────┐
              │   internal/domain        │   │  internal/worker     │
              │   （领域层：model+service）│◀──│  （后台计算）         │
              └───────┬──────────────────┘   └──────────────────────┘
                      │ 依赖存储接口（Repository 接口）
              ┌───────▼──────────────────┐
              │   internal/storage       │
              │   （存储层：接口+内存/SQLite实现+迁移）│
              └──────────────────────────┘

   internal/parser（解析层）：规则文件 → 领域模型（被 API 层调用）
   internal/check（检查层）：启动自检 + 按需完整检查（调用领域/存储接口）
   internal/config（配置层）：全局配置加载（被各层引用，无反向依赖）
```

## 2. 分层职责与依赖规则

### 2.1 解析层（internal/parser）

| 职责 | 说明 |
| --- | --- |
| 格式探测 | 依据内容特征识别 CSV / JSON / YAML |
| 规则解析 | 将原始数据解析为 `domain.Rule` 列表 |
| 格式校验 | 必填字段、IP/CIDR、端口、动作、优先级 |
| 错误定位 | 错误信息携带 行号/字段 定位 |

- 只依赖 `internal/domain/model`（产出模型）与标准库；
- **不感知**存储、API、任务。

### 2.2 领域层（internal/domain）

包含 `model`（Rule、Network、Analysis 等纯数据结构）与 `service`（四大分析 + 引擎）。

- `CoverageService` / `ConflictService` / `RedundancyService` / `ReachabilityService`：纯计算逻辑，输入输出均为领域模型，**无副作用**，可单测；
- `Engine`：编排层。组装规则子集、调用各服务、维护 `rulesetVersion`、产出统一 `AnalysisResult`；
- 领域层依赖 `Storage.Repository` **接口**（而非具体实现），用于读取规则与持久化结果——这是唯一的"领域→存储"引用，且方向是接口倒置。

### 2.3 存储层（internal/storage）

- `Repository` 接口：规则 CRUD、任务 CRUD、结果 CRUD、审计日志、迁移版本；
- `MemoryStore`：进程内实现（map + 互斥锁），默认存储，适合演示与测试；
- `SQLiteStore`：`modernc.org/sqlite` 纯 Go 驱动，持久化实现，参数化查询；
- `Migrator`：版本化迁移执行器（读取 `schema_migrations`，按版本号顺序应用 DDL）；
- 存储层**不感知**业务分析逻辑。

### 2.4 API 层（internal/api）

- `Server`：HTTP 服务器装配（路由、中间件、静态资源挂载）；
- `Router`：路径 → handler 映射，统一前缀 `/api/v1`；中间件（请求日志、`X-User` 审计头、panic 恢复、统一错误响应）在本文件实现；
- `Handlers`：参数绑定（DTO 结构定义在本文件）、调用领域服务/任务管理、响应封装、错误码映射；
- 调用 `check.Checker` 暴露 `/checks` 端点（完整检查）。

### 2.5 后台计算层（internal/worker）

- `Manager`：任务队列、Worker 池、状态机、重试、并发控制；
- 任务执行器按类型分发到领域服务的异步入口（`Engine.RunAsync`）；
- 结果写回存储（`Repository.SaveResult` + 更新任务状态）。

### 2.6 检查层（internal/check）

- `Checker`：执行 4 类检查（格式 / 引用 / 一致性 / 结果快照），产出 `CheckReport`；
- 由 `main` 在启动时调用（自检），也由 API 按需触发。

### 2.7 配置层（internal/config）

- 解析命令行标志与环境变量：`addr`、`store`（memory/sqlite）、`dbPath`、`defaultAction`、`workerCount`、`maxRulesSync` 等；
- 提供 `Config` 结构体贯穿装配。

## 3. 模块依赖矩阵（简化）

| 模块 | 依赖 |
| --- | --- |
| cmd/server | config, api, worker, storage, check, parser |
| api | domain, worker, storage(仅通过 domain 接口), config, parser, check |
| worker | domain, storage |
| domain.service | domain.model, storage(接口) |
| domain.model | （无） |
| storage | domain.model, config |
| parser | domain.model |
| check | domain, storage |

禁止反向依赖：`domain` 不 import `api` / `worker` / `parser` 的具体包；`storage` 不 import `api`。

## 4. 关键接口设计（伪代码级约定）

```go
// storage 层接口（领域层面向它编程）
type Repository interface {
    // 规则
    SaveRules([]model.Rule) error
    ListRules(filter RuleFilter) ([]model.Rule, error)
    GetRule(id string) (model.Rule, bool)
    DeleteRule(id string) error
    ReplaceAllRules([]model.Rule) error
    RulesetVersion() int
    // 任务
    CreateTask(t *model.AnalysisTask) error
    UpdateTask(t *model.AnalysisTask) error
    GetTask(id string) (model.AnalysisTask, bool)
    ListTasks(filter TaskFilter) ([]model.AnalysisTask, error)
    // 结果
    SaveResult(r *model.AnalysisResult) error
    GetResult(taskID string) (model.AnalysisResult, bool)
    // 审计日志 / 迁移
    AppendAuditLog(e model.AuditLog) error
    ListAuditLogs(limit int) ([]model.AuditLog, error)
    MigrationVersion() (int, error)
    ApplyMigration(version int, ddl string) error
    Close() error
}

// 领域服务：无副作用纯计算
type AnalysisService interface {
    Analyze(rules []model.Rule, params map[string]any) (*model.AnalysisResult, error)
}

// 后台任务执行器
type TaskRunner interface {
    Run(ctx context.Context, task *model.AnalysisTask) error
}
```

## 5. 数据流

### 5.1 规则导入流程

```
前端/curl → POST /rules/import
  → api.Handlers.ImportRules
  → parser.FormatDetector.Detect(原始数据)
  → parser.RuleParser.Parse(format, data) → []model.Rule + 校验错误
  → (模式=replace) storage.Repository.ReplaceAllRules / (模式=append) SaveRules
  → 写审计日志（AuditLog{Action: import, ...}）
  → 响应 { imported: n, errors: [...] }
```

### 5.2 同步分析流程（小规模）

```
POST /analysis/{type}（type ∈ coverage|conflicts|redundancy|reachability，规则数 ≤ maxRulesSync）
  → api.Handlers → domain.Engine.Analyze(type, ruleSubset, params)
  → 领域服务纯计算 → model.AnalysisResult
  → 响应直接返回结果
```

### 5.3 异步分析流程（大规模 / matrix）

```
POST /analysis/tasks {type, params}
  → api.Handlers → Repository.CreateTask(pending)
  → worker.Manager.Enqueue(taskID)
  → Worker 池领取 → Engine.RunAsync → 领域服务计算 → Repository.SaveResult + UpdateTask(success)
  → 前端轮询 GET /analysis/tasks/{id} → 就绪后 GET /analysis/results/{id}
```

### 5.4 数据迁移流程

```
启动时：Migrator.Up(storage) → 按版本顺序应用 DDL
命令：  netpolicy migrate-up | export -o out.json | import -i in.json
API：   GET /api/v1/migrate/export → JSON 包
        POST /api/v1/migrate/import → 恢复数据
```

## 6. 技术选型

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | Go 1.22+ | 部署简单、并发模型契合 Worker 池 |
| HTTP | 标准库 `net/http` + `http.ServeMux`（Go 1.22 支持方法路由） | 零依赖、代码量可控 |
| SQLite | `modernc.org/sqlite`（纯 Go，无 CGO） | 免编译依赖、便于迁移演示 |
| 前端 | 原生 HTML/CSS/JS 单页 + `fetch` 轮询 | 无需构建工具链，简单直观 |
| 队列 | 进程内 channel + 状态表 | 单机场景足够，避免引入消息中间件 |
| 测试 | 标准库 `testing` + `net/http/httptest` | 表格驱动、无框架依赖 |
