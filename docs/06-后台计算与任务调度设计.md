# 06 后台计算与任务调度设计

## 1. 设计动机

四大分析中，覆盖/冲突/冗余为 O(n²) 级两两比较，可达性矩阵为 O(源×目标×端口×规则)，当规则量达万级时同步计算会阻塞 HTTP 请求。因此引入**后台计算**：

- 大规模分析一律异步化，API 立即返回 `taskId`，前端轮询；
- 小规模分析（规则数 ≤ `maxRulesSync`，默认 2000）可同步直出结果，减少一次轮询；
- 统一的任务状态机保证可追踪、可重试、可恢复。

## 2. 总体结构

```
                    ┌─────────────────────────────────────────┐
   API 层            │              worker.Manager             │
 POST /tasks ──────▶ │  ┌──────────┐   ┌────────────────────┐  │
                    │  │ 任务队列   │──▶│ Worker 池（N 个）    │  │
                    │  │ chan      │   │  for { 领取 → 执行 }  │  │
                    │  └──────────┘   └─────────┬──────────┘  │
                    │                            │             │
                    │             domain.Engine.RunAsync(...)  │
                    │                            │             │
                    │             storage.Repository.SaveResult│
                    └────────────────────────────┼────────────┘
                                                 ▼
                                    analysis_task / analysis_result 表
```

- 任务队列：带缓冲的 `chan string`（taskID），容量 = 2 × workerCount；
- Worker 池：`workerCount` 个 goroutine（默认 4），启动时创建、退出时优雅关闭；
- 任务状态持久化在存储层，队列只是"内存加速"，**以存储状态为准**（崩溃恢复依据）。

## 3. 任务状态机

```
                     ┌────────────── retry(≤2) ──────────────┐
                     ▼                                       │
  create ──▶ pending ──▶ running ──▶ success
                 │         │  ▲        │
                 │         │  └─失败────┘(retryCount>=2)
                 │         ▼
                 │      failed（可手动 retry，重置 pending）
                 └─ cancel ─▶ canceled（仅 pending/running 可取消，可选实现）
```

| 状态 | 含义 | 迁移条件 |
| --- | --- | --- |
| pending | 已入库待执行 | 入队成功 |
| running | Worker 领取，执行中 | 出队即置 running（先写库再开始计算，防重复领取） |
| success | 执行完成，结果已入库 | Runner 返回 nil |
| failed | 执行失败（或服务中断） | Runner 返回 error 且重试耗尽；或重启时清理 running→failed(interrupted) |
| canceled | 被取消 | 仅在取消接口触发（本期提供 POST retry，cancel 为预留） |

**关键点——领取的原子性**：
1. Worker 从队列拿到 taskID；
2. `CompareAndSetStatus(taskID, "pending" → "running")`（存储层实现，内存版用锁、SQLite 版用条件 UPDATE）；
3. 只有 CAS 成功者执行；否则丢弃（说明已被其他 Worker 领取或已取消）。

## 4. 执行器分发

`Manager` 内维护类型 → 执行函数的映射：

```go
runners := map[string]TaskRunner{
    "coverage":     engineRunner(coverage),
    "conflicts":    engineRunner(conflicts),
    "redundancy":   engineRunner(redundancy),
    "reachability": engineRunner(reachability),
    "matrix":       matrixRunner,        // 分片并行
    "whatif":       whatifRunner,        // 影子规则集
    "simulate":     simulateRunner,      // 内存仿真，不落库结果
}
```

执行流程（每个任务）：
1. 从任务 `Params` 反序列化参数（规则子集、目标空间、场景矩阵等）；
2. 读取当前规则集快照（读取时锁定 `ruleset_version`，见 BR-9）；
3. 调用领域服务计算；
4. `SaveResult` → `UpdateTask(success, finishedAt, error="")`；
5. 失败：`UpdateTask(failed, error)`，`retryCount < 2` 时自动重新入队（`pending`）。

## 5. 并发与资源控制

- **并发上限**：同时执行的任务数 = workerCount；队列满时 `Enqueue` 阻塞（由 API 层设置超时，避免无限挂起）；
- **单任务超时**：`taskTimeout`（默认 5 分钟），超时后标记 failed 并释放 Worker（通过 `context.WithTimeout` 取消执行器）；
- **矩阵分片**：`matrix` 任务按"源"分片，每个分片为一个子计算，Worker 内顺序执行、结果合并——不额外开 goroutine（避免无界并发），仅用于进度细化；
- **取消传播**：`context` 贯穿执行器，Worker 关闭时取消进行中任务（标记 failed(interrupted)）。

## 6. 失败与容错

| 场景 | 处理 |
| --- | --- |
| 计算 panic | Worker 用 `defer recover` 捕获 → 任务 failed，错误信息含 panic 摘要 |
| 单次失败 | retryCount+1，自动重新入队（≤2 次，指数退避 1s/2s） |
| 重试耗尽 | 状态 failed，保留 error，可手动 `POST /tasks/{id}/retry` |
| 服务重启 | 启动时扫描 running 任务 → 置 failed(interrupted)；pending 任务重新入队 |
| 结果写失败 | 视为执行失败，走重试（保证"任务成功则必有结果"的不变量） |
| 规则集在任务执行中被变更 | 任务使用提交时快照（读取规则列表到内存），不受影响 |

## 7. 存储状态与接口

```go
// worker 依赖的存储能力（Repository 接口子集）
CreateTask(task) error
GetTask(id) (AnalysisTask, bool)
UpdateTask(task) error          // 整体更新（含状态迁移校验）
ListPendingTasks() ([]AnalysisTask, error)   // 重启恢复用
CASStatus(id, from, to string) (bool, error) // 领取原子性
SaveResult(result) error
```

**状态迁移校验**：`UpdateTask` 拒绝非法迁移（如 `success → running`），存储层实现 `validTransitions` 表，违反时返回 `CONFLICT`。

## 8. 与 API 的交互时序

```
POST /api/v1/analysis/tasks
  ├─ 校验参数（类型合法、规则子集存在）
  ├─ Repository.CreateTask(pending)
  └─ Manager.Enqueue(taskID)          // 立即返回 202 语义（{taskId, status:"pending"}）

GET /api/v1/analysis/tasks/{id}       // 任意时刻可查
GET /api/v1/analysis/results/{id}     // success 后可用；非 success 返回 TASK_NOT_READY(409)
```

> 前端轮询策略见 `docs/07`：首次 500ms，之后 1s 固定间隔，success/failed 即停。

## 9. 规模与性能预期

| 场景 | 规模 | 方式 | 预期 |
| --- | --- | --- | --- |
| 冲突检测 | 1,000 条 | 同步 | < 1s |
| 冲突检测 | 10,000 条 | 异步（4 Worker） | 数秒级 |
| 可达性矩阵 | 50 源 × 50 目标 × 10 端口 = 25,000 场景 | 异步分片 | 数秒级 |
| 覆盖分析 | 10,000 条 | 异步 | 秒级 |

> 以上为设计预期；基准测试（见 08 文档）负责在实现后验证。
