# 08 测试与完整性检查设计

## 1. 测试总体策略

| 层级 | 范围 | 方式 | 位置 |
| --- | --- | --- | --- |
| 单元测试 | 解析、CIDR 运算、四大分析服务 | 表格驱动 + 基准测试 | 各包内 `*_test.go` |
| 集成测试 | API + 存储（内存与 SQLite 双跑） | `net/http/httptest` | `internal/api` |
| 端到端场景 | 导入 → 分析 → 任务 → 迁移 全链路 | 脚本化集成测试 | `internal/e2e`（或 api 包内） |
| 基准测试 | 冲突 O(n²)、矩阵可达性 | `testing.B` | domain/service |

> 测试代码不计入 2000–2200 行约束，可充分编写。

## 2. 单元测试计划

### 2.1 parser 包
- 格式探测：JSON / CSV / YAML / 未知格式 → 正确识别或报错；
- CSV 解析：列头缺失、缺列、多余列、空行、转义引号；
- JSON/YAML 解析：字段缺省（默认值：priority=100、port=1-65535、protocol=any）；
- 校验规则：
  - 非法 CIDR（`10.0.0.999`、`300.1.1.1`）、非法端口（0、70000、from>to）；
  - 非法动作、非法协议、优先级 < 1；
  - 错误信息携带行号与字段名；
- 归一化：单 IP → /32。

### 2.2 domain/service 包
- **覆盖**：
  - 全覆盖（目标空间全部被规则命中）→ ratio=1.0、无未覆盖；
  - 半覆盖（部分子网无规则）→ 输出正确未覆盖 CIDR；
  - 多规则重叠 → redundantRatio 正确；
  - 目标空间显式指定 vs 自动推导。
- **冲突**：
  - 完全冲突（相等条件相反动作）→ CRITICAL；
  - 部分冲突（交叉）→ HIGH，重叠区间描述正确；
  - 包含冲突（优先级不同）→ MEDIUM；
  - 同动作不报冲突；跨策略集默认不报（配置开启后报）；
  - 空规则集 → 空结果不 panic。
- **冗余**：
  - 完全重复 → 类型 repeat；
  - 被遮蔽（高优先级宽规则 + 低优先级窄规则同动作）→ shadowed；
  - 被泛化（多规则联合覆盖）→ generalized；
  - 动作不同不判冗余；
  - 默认策略影响（default-allow 下 deny 规则的遮蔽语义）正确。
- **可达性**：
  - 直连 allow / 直连 deny / 无命中 default；
  - 命中规则链按优先级排序且只取第一条生效；
  - 端口范围命中（80-90 命中 443 否）；
  - 协议过滤（any 匹配 tcp，tcp 不匹配 udp）；
  - 矩阵：M×N×K 场景计数与结果正确性抽查；
  - whatif：模拟删除规则后 verdict 翻转的 diff 正确。

### 2.3 storage 包
- Memory 与 SQLite 各跑一遍同一套 Repository 用例（接口一致性测试）：
  - SaveRules / ListRules / GetRule / DeleteRule / ReplaceAllRules；
  - rulesetVersion 递增（append 与 replace）；
  - 任务 CRUD 与状态迁移校验（非法迁移拒绝）；
  - CASStatus 原子性（并发领取只有一个成功）；
  - 结果存取、审计日志追加与查询。

### 2.4 worker 包
- 队列满时 Enqueue 阻塞/超时行为；
- Worker 池并发执行 N 个任务全部完成；
- 失败重试（≤2 次后 failed）；
- 重启恢复：running → failed(interrupted)、pending 重新入队；
- 任务超时取消。

## 3. 集成测试计划（api 包）

用 `httptest.NewServer` 装配真实 Server（MemoryStore），覆盖：

1. **导入全链路**：合法 JSON 导入 → 列表可见 → 统计正确；
2. **导入失败回滚**：含一条坏数据的批次 → imported=0，规则数不变；
3. **同步分析**：POST coverage/conflicts/redundancy/reachability → 断言结果字段；
4. **异步任务**：提交 matrix → 轮询状态 → success → 取结果 payload；
5. **TOO_MANY_RULES 降级**：超过 maxRulesSync 的同步请求返回 422；
6. **完整检查**：故意插入孤儿结果 → GET /checks 报 warn；
7. **迁移**：导出 → 清空 → 导入 → 规则/任务/结果恢复、version 一致；
8. **审计**：导入/删除后 GET /audit 可见记录（含 X-User）；
9. **错误码**：404（不存在规则/任务）、400（坏参数）、409（非法状态迁移）。

SQLite 变体：将 `-store sqlite` 的实例以临时文件跑同一套关键用例（1/2/4/7），验证持久化路径。

## 4. 基准测试计划

| 基准 | 规模 | 断言目标 |
| --- | --- | --- |
| BenchmarkConflict1000 | 1,000 条规则冲突检测 | < 1s/op |
| BenchmarkConflict10000 | 10,000 条规则（异步路径估算） | 可接受秒级 |
| BenchmarkCoverage10000 | 10,000 条覆盖分析 | < 5s |
| BenchmarkMatrix | 50×50×10 场景矩阵 | < 10s |
| BenchmarkParse | 10,000 条 JSON 导入 | < 5s |

> 基准结果为文档记录值，不作为 CI 硬性门槛（演示环境机器差异大）。

## 5. 完整检查（check.Checker）设计

### 5.1 检查分类

| 类别 | 检查项 | 判定 |
| --- | --- | --- |
| rule_format | 每条规则的字段再次通过 parser 校验 | 不通过 → fail |
| rule_format | 端口范围合法、动作/协议枚举合法 | fail |
| reference | 结果引用的 task 必须存在（孤儿结果） | 存在孤儿 → warn |
| reference | 规则引用的 policySet 在策略集表中存在（若启用策略集表） | warn |
| consistency | 规则 ID 唯一、无空必填字段 | fail |
| consistency | rulesetVersion 与"最近一次写入"一致（无并发漂移） | warn |
| consistency | 迁移版本 = 定义的最新版本 | 不一致 → fail（启动自检阻断） |
| result | 结果.rulesetVersion == 当前 rulesetVersion（过期结果标记 stale） | 有 stale → warn |

### 5.2 检查报告结构

```go
type CheckReport struct {
    RunAt    time.Time
    Passed   int
    Warnings int
    Failed   int
    Items    []CheckItem  // {Category, Name, Level(pass|warn|fail), Detail}
}
```

### 5.3 触发时机

1. **启动自检**（main）：配置加载 → 存储连接 → 迁移执行 → `Checker.Run()`；任一 fail → 启动失败（`SERVICE_UNAVAILABLE`），运行中可继续服务但 `/health` 标记 degraded；
2. **按需**：`GET /api/v1/checks`，报告落库（最新一份可查 `GET /checks/latest`）；
3. **变更后**：每次全量导入成功后自动执行一次轻量自检（仅 rule_format + consistency），结果并入导入响应（可选字段 `checkSummary`）。

### 5.4 修复建议模板

- 孤儿结果：`DELETE 结果或补回任务记录`；
- stale 结果：`重新运行对应分析任务`；
- 迁移版本落后：`执行 netpolicy migrate-up`。
